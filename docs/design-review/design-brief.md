# Claude Fable 独立設計ブリーフ

## 役割

あなたはAIエージェント基盤の主任アーキテクトです。既存の設計案をレビューするのではなく、以下の課題からゼロベースで独立設計してください。

## 独立性の制約

- `REQUIREMENTS.md`は読まない。
- `別プロジェクトの設計資料`も読まない。
- ローカルファイル、Git履歴、過去の会話を調査しない。
- このブリーフに書かれた事実だけを前提にする。
- 実装、ファイル編集、コマンド実行、外部操作は行わない。

## 背景

利用者は、CodexとClaude Codeを使って複数のローカル開発・業務自動化案件を進めている。現在は利用者本人が、タスク分解、担当AIへの割当、進捗確認、再指示、レビュー、検証、成果統合を行っている。

これを、マネージャーAIが複数の子エージェントを統括する「AI Orchestrator MVP」へ移したい。

既存環境には以下がある。

- Codexのネイティブ・サブエージェント機能
- Claude Code CLI
- ローカルGitリポジトリ
- `AGENTS.md`、ルール、スキル、`HANDOFF.md`によるファイルベースの引き継ぎ
- テスト、lint、秘密情報検査などの機械ゲート

Claudeは常時必須ではなく、クレジットに余裕がある場合の独立レビュー担当として使う。Claudeが利用不能でも基本フローは成立させる。

## 最重要の懸念

1. 複数エージェントでクレジット消費が暴走する。
2. 親会話のコンテキストが肥大化し、重要な制約が埋もれて質が落ちる。
3. 再試行、レビュー、待機が収束せず作業が終わらない。
4. 並列編集でユーザーの未コミット変更を壊す。
5. 子エージェントの誤った「完了」をManagerが信じる。
6. 本番変更、外部送信、秘密情報の漏えいなど権限事故を起こす。

## MVPの対象

- ユーザーが明示起動するローカルGitリポジトリの非本番コード修正
- 調査、実装、読み取り専用レビュー、決定論的検証、結果統合
- 失敗時の停止、再開、監査

## MVPの対象外

- 本番デプロイ、外部サービスへの書き込み
- `main`への自動マージ、リモートpush
- 24時間常駐する完全自律デーモン
- GUIダッシュボード
- 複数リポジトリをまたぐ同時実装

## 必須設計課題

以下を、実装可能な粒度で独立設計すること。

1. Managerと子エージェントの責務・権限境界
2. タスク規模に応じて、単一エージェント／複数エージェントを選ぶ判断方法
3. runの状態機械と、必ず終端状態へ到達する停止条件
4. retry、review loop、timeout、cancel、resumeのルール
5. クレジットとコンテキストのbudget envelope
6. 親へ生出力を集めずに成果を統合するartifact設計
7. dirty worktree、stale commit、並列編集競合へのGit安全設計
8. 子の完了報告を検証する証拠・Verifier設計
9. Claudeを任意の異種モデルreviewerとして差し込む境界
10. prompt injection、秘密情報、外部変更、破壊的コマンドへの防御
11. 途中停止後に新しいManagerセッションで再開する方法
12. MVPが過剰設計にならない最小構成

## 求める出力

日本語Markdownで、以下の順に出力する。

### 1. 結論

推奨アーキテクチャと、なぜそれがMVPとして適切かを5行以内。

### 2. 設計原則

5〜10件。各原則がどの事故を防ぐかも記載。

### 3. 全体構成

テキスト図と、各コンポーネントの責務。

### 4. 実行フローと状態機械

正常系と、budget超過、timeout、review未収束、dirty worktree、cancel、resumeを含める。

### 5. Role contract

Manager、Researcher、Implementer、Reviewer、Verifierについて、入力、許可、禁止、出力、完了条件を表形式で示す。

### 6. コスト・コンテキスト制御

具体的な既定値とhard capを提案する。正確なクレジット残量が取得できない場合の代理指標も含める。

### 7. Artifactとschema

最低限必要なファイル構成、run manifest、agent result、event log、checkpointの項目を示す。

### 8. 安全境界

Always / Ask first / Neverで整理する。

### 9. 主要リスク

重大度、発生条件、検知、予防、回復を含むリスク表。

### 10. 受入テスト

正常系だけでなく、budget超過、無応答、壊れた子出力、stale checkpoint、prompt injection、孤児プロセスを含む。

### 11. MVPとPhase 2の境界

初版に入れるものと、後回しにすべきものを明確に分ける。

### 12. 実装前に利用者が決めること

最大5件。各項目に推奨初期値を付ける。

## 品質条件

- 抽象論だけで終わらず、検証可能な停止条件と既定値を出す。
- 「AIがうまく判断する」に依存しない。
- クレジット削減のために必要な独立レビューまで削らない。
- 承認を残すことを未熟さと扱わない。
- 実装の容易さ、保守性、事故時の復旧を同時に評価する。
