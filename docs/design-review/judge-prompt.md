# AI Orchestrator 設計案ブラインド比較審査

あなたはAIエージェント基盤の審査員です。2つの独立成果物を比較し、採用判断の材料を作ってください。あなた自身はどちらの案の著者でもないものとして振る舞い、著者の推定を行わず、モデル名・ファイル名・文体による加点減点を一切しないでください。

注意: 一方は要件定義の体裁、もう一方は設計書の体裁で書かれています。体裁・網羅行数ではなく、防御の実効性と実装可能性という中身で比較してください。

## 読むファイル（この3つ以外は一切読まない。ディレクトリ一覧も取らない）
1. 審査基準の正本: docs/design-review/design-brief.md（特に「最重要の懸念」6件と「品質条件」）
2. 案A: /tmp/orc-judge/DESIGN_A.md
3. 案B: /tmp/orc-judge/DESIGN_B.md

Git履歴・過去会話・他のローカルファイルは読まない。実装・ファイル編集・git操作・外部操作はしない。出力はチャット応答のみ。

## 審査基準（この順で重み付け）
1. 6懸念への防御力: クレジット暴走／親コンテキスト肥大／非収束／並列編集によるユーザー未コミット変更の破壊／子の偽完了／権限事故。各懸念について「構造で防いでいるか、プロンプト指示（散文）に依存しているか」を区別して評価する。
2. 停止性: すべてのループが有界か。停止条件が機械的（カウンタ・timeout・cap）か、AIの判断依存か。
3. 具体性: 既定値・hard cap・schema・受入テストが検証可能な粒度で書かれているか。抽象論は減点。token/credit実測が取れない場合にfail-loudかも見る。
4. MVP適正: 実装容易性・保守性・事故時復旧。過剰設計（キュー基盤・常駐・GUI等をMVPに入れていないか）と、文書自体の肥大による実装者のコンテキスト負荷も減点対象。
5. ブリーフ要件の網羅: 12の必須設計課題の充足、Claude任意reviewer化（不在時のCodex単独縮退）、resume、監査。

## 出力形式（日本語）
1. 総評: A/Bそれぞれ3行以内。
2. 懸念別比較表: 6懸念 × A/B。各セルは「防御方式(構造/散文)・具体度・穴」を1行で。優劣を◎○△×で付ける。
3. 停止性・budget・Git安全・resumeの深掘り比較: 数値既定値レベルで突き合わせ、片方にしかない防壁を列挙する（引用は節・見出し名で示す）。
4. 両案共通の穴: どちらも見落としているリスクを最大5件。ここが審査の最重要成果物。
5. 判定: A採用／B採用／Aベース統合／Bベース統合のいずれかと理由。
6. 統合提案: 判定でベースにした案へ、もう一方から移植すべき要素トップ5（移植先の節付き）。
7. 不足受入テスト: 両案どちらにもない受入テストを最大5件（入力、注入する障害、期待状態、確認証拠）。
8. 確信度: 判定の確信度（高/中/低）と、判定が変わりうる条件。

## 禁止
- 根拠なく「どちらも良い」で終えること（判定を必ず出す）
- 案に書かれていない機能を書かれているとみなすこと（節・見出しを引用できる指摘のみ有効）
- 文字数・網羅性だけで優劣を付けること（防御の実効性で判定する）
- 著者の推定・言及（「これは〇〇が書いた案」等）
